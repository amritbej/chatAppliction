# Payment System Documentation

## 1. Overview
ChatApp features a secure, real-time peer-to-peer (P2P) payment architecture integrated into chat rooms. Payments are verified strictly server-side using payment gateway cryptographic signatures and webhook reconciliations.

The system is designed with a provider-agnostic interface (`PaymentProvider`), with out-of-the-box support for:
1. **Razorpay Sandbox / Live** (Default for INR payments via UPI, Cards, Netbanking).
2. **Deterministic Mock/Test Provider** (Enables local offline development and automated testing without external network access).

---

## 2. Core Security & Design Principles

1. **Never Trust Client-Reported Success**:
   The client application cannot report a payment as successful. The server strictly verifies the cryptographic HMAC-SHA256 signature generated by the payment gateway against the server's secret key.
2. **Minor Currency Units (Paise)**:
   All monetary amounts are stored and calculated as integers in the currency's minor units (e.g. ₹100.50 is stored as `10050` paise). This eliminates floating-point rounding bugs.
3. **Transaction State Machine**:
   Every payment follows an explicit lifecycle:
   ```
   [created] -> [pending] -> [processing] -> [success]
                                          -> [failed]
                                          -> [cancelled]
                               [success] -> [refunded]
   ```
4. **Idempotency & Duplicate Protection**:
   - Order creation and verification requests enforce idempotency keys.
   - Unique database indexes on `providerOrderId` and `providerPaymentId` prevent duplicate credits or replay attacks.
   - Webhook processing is idempotent: duplicate webhook events return HTTP 200 without double-crediting.
5. **Configurable Transaction Limits**:
   Minimum and maximum payment bounds are enforced server-side via environment variables:
   - `MIN_PAYMENT_AMOUNT`: e.g. `100` (₹1.00)
   - `MAX_PAYMENT_AMOUNT`: e.g. `10000000` (₹100,000.00)

## 3. Payment Lifecycle & Step-by-Step Flow

### Step 1: Order Creation (`POST /api/payments/orders`)
- **Request Body**:
  ```json
  {
    "recipientId": "65b...",
    "roomId": "65c...",
    "amount": 500,
    "note": "Lunch payment",
    "idempotencyKey": "uuid-v4-optional"
  }
  ```
- **Server Validations**:
  - Authenticated user cannot pay themselves (`sender !== recipient`).
  - Recipient must exist and both users must be members of `roomId`.
  - Amount must be within `[MIN_PAYMENT_AMOUNT, MAX_PAYMENT_AMOUNT]`.
- **Database Action**:
  - Creates a `Transaction` document with status `"created"`.
  - Minor units calculated: `amountMinor = Math.round(amount * 100)`.
- **Gateway Action**:
  - Calls `provider.createOrder(amountMinor, currency, receiptId)`.
  - Updates transaction with `providerOrderId` and moves status to `"pending"`.
- **Response**:
  ```json
  {
    "success": true,
    "data": {
      "transactionId": "TXN_171...",
      "orderId": "order_EKf38glq5nfQ",
      "amount": 50000,
      "currency": "INR",
      "key": "rzp_test_..."
    }
  }
  ```

### Step 2: Gateway Checkout & Client Processing
- In Web / Mobile, the user completes checkout through Razorpay checkout modal.
- Gateway returns:
  - `razorpay_payment_id`
  - `razorpay_order_id`
  - `razorpay_signature`

### Step 3: Verification (`POST /api/payments/verify`)
- Client sends the returned payload to the server.
- **Server Cryptographic Verification**:
  - Generates expected signature:
    `HMAC_SHA256(order_id + "|" + payment_id, secret)`
  - Uses timing-safe string comparison (`crypto.timingSafeEqual`).
- **State Transition & Message Creation**:
  - Transaction status transitioned to `"success"` with `completedAt = new Date()`.
  - Automatically creates a chat message in `roomId` with `type: "payment"`, referencing the transaction.
  - Broadcasts `payment:success` and `message:receive` over Socket.IO.

### Step 4: Webhook Reconciliations (`POST /api/payments/webhook`)
- Razorpay sends asynchronous webhook events (e.g. `payment.captured`, `payment.failed`).
- Server verifies webhook signature using `RAZORPAY_WEBHOOK_SECRET`.
- Reconciles transaction status asynchronously in case of network interruption between client and server.

## 4. Chat Payment Message Structure
Payment messages reference the transaction record without duplicating unbounded historical data:
```json
{
  "_id": "660...",
  "room": "65c...",
  "sender": { "_id": "65a...", "username": "alice" },
  "type": "payment",
  "content": "Payment of ₹500",
  "payment": {
    "transactionId": "TXN_171...",
    "amount": 50000,
    "currency": "INR",
    "status": "success",
    "note": "Lunch payment"
  },
  "createdAt": "2026-09-28T10:00:00.000Z"
}
```

---

## 5. Refunds Flow (`POST /api/payments/:transactionId/refund`)
- Authorized user (sender or admin) initiates a refund request with optional reason.
- Server validates that the transaction is in `"success"` state and not previously refunded.
- Payment provider executes gateway refund.
- Transaction transitions to `"refunded"`.
- Socket event `payment:refunded` emitted to chat room.
